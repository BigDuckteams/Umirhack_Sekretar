# Онлайн-деканат — цифровой секретарь

Студент присылает **фото справки или заявления** и задаёт вопрос. Сервис **читает документ (OCR)**, **заполняет карточку полей**, **отвечает по Положению со ссылкой на пункт** и показывает, где на снимке найдено каждое поле. Если ответа нет ни в документе, ни в Положении — честно говорит об этом.

```
фото/скан/PDF + вопрос
   │
   ├─ предобработка: поиск листа, выпрямление наклона до ±45°, выравнивание тени, блики, перебор вариантов
   ├─ OCR (Tesseract, rus+eng)          ← внешние API не используются, всё работает на CPU ноутбука
   ├─ тип документа: автоопределение или выбор вручную
   ├─ карточка полей (метки → шаблоны → запасные детекторы; подпись и печать — по изображению)
   ├─ поиск по Положению: какие пункты относятся к этому документу и что в них обязательно
   └─ ответ: «в порядке» / «не хватает …» / «ответа нет» + источник (пункт Положения или поле документа)
```

Три вида ответов — как в ТЗ:

| Вердикт | Пример ответа |
|---|---|
| **Документ в порядке** | «Справка содержит все данные, которые требует п. 3.2 Положения. Окончательное решение примет сотрудник деканата.» |
| **Чего-то не хватает** | «Не хватает даты выдачи и печати вуза. Эти поля обязательны по п. 3.4 Положения.» |
| **Ответа нет** | «В документе и в Положении нет информации по вопросу «Сколько стоит обучение?». Обратитесь в деканат.» |

> Для работы нужны **только Python и Tesseract**. Никаких облачных сервисов, ключей и скачивания моделей при запуске.

## Что сделано по ТЗ

**Базовый уровень (обязательно)**

| № | Требование | Где и как |
|---|---|---|
| 1 | Принять документ и вопрос (JPG, PNG, PDF; вопрос на русском) | веб-страница, `POST /api/analyze`, CLI `ask` / `batch`; PDF — до 5 страниц |
| 2 | Распознать текст с помощью OCR | Tesseract 5 (`dekanat/ocr/`) |
| 3 | Заполнить карточку полей выбранного типа; нет поля — «не найдено» | `dekanat/extract/`, типы описаны в `config/doc_types/*.yaml` |
| 4 | Ответить по полям документа и пунктам Положения | `dekanat/qa/`, `dekanat/kb/` |
| 5 | Указать источник: номер пункта или поле документа | у каждого ответа `sources` (пункт Положения / поле + рамка на снимке) |
| 6 | Не выдумывать | ответ собирается только из найденных полей и дословного текста пунктов; нет данных → «ответа нет» |

Тип документа можно выбрать вручную (или оставить автоопределение). Интерфейс — веб-страница.

**Бонусы (продвинутый уровень)**

| Бонус | Реализация |
|---|---|
| Автоопределение типа | ключевые фразы и «покрытие полей» из конфига типа (`dekanat/classify.py`) |
| Плохие снимки | поиск листа и перспектива, выпрямление наклона, нормализация освещения, перебор вариантов, поворот 90/180°, повышение разрешения (`dekanat/ocr/`) |
| Новый тип без кода | описание полей в YAML; редактор прямо в интерфейсе («Типы документов») |
| Подсветка на снимке | рамки каждого поля на исходном фото; клик по строке карточки → фрагмент на снимке |

## Быстрый старт

### 1. Установите Tesseract с русским языком

* **Windows:** установщик [UB Mannheim](https://github.com/UB-Mannheim/tesseract/wiki) — при установке отметьте язык **Russian**. Сервис сам найдёт `C:\Program Files\Tesseract-OCR\tesseract.exe` (можно задать путь в `config/settings.yaml` → `ocr.tesseract_cmd` или переменной `TESSERACT_CMD`).
* **Linux:** `sudo apt install tesseract-ocr tesseract-ocr-rus tesseract-ocr-osd`
* **macOS:** `brew install tesseract tesseract-lang`

### 2. Поставьте зависимости

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows;  Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python -m dekanat doctor        # проверка окружения
```

Нужен Python 3.10 или новее (проверено на 3.14).

### 3. Запустите

```bash
python -m dekanat serve         # → http://127.0.0.1:8000
```

Откройте страницу, кликните по примеру на столе (или перетащите своё фото) и задайте вопрос.

Готовый интерфейс (React) уже собран и лежит в `dekanat/web/static/app/` — **Node.js для запуска не нужен**. Он нужен только тем, кто хочет править интерфейс (см. «Интерфейс на React»).

### Docker (по желанию)

```bash
docker build -t online-dekanat .
docker run -p 8000:8000 online-dekanat
```

`Dockerfile` написан по описанию и в среде разработки **не собирался** — Tesseract в нём ставится из `apt`. В контейнере редактирование типов документов и Положения из интерфейса выключено (`DEKANAT_SERVER_ALLOW_EDIT=false`).

## Как пользоваться

### Веб-интерфейс: «Стол декана»

Слева — **диалог** с цифровым секретарём, справа — **стол с документом**. Всё, что требует ТЗ, на виду:

| Требование ТЗ | Где в интерфейсе |
|---|---|
| Принять документ (JPG/PNG/PDF) и вопрос на русском | перетащить файл на стол, «Выбрать файл», скрепка в панели ввода, вставка из буфера (`Ctrl+V`), камера на телефоне; поле вопроса внизу |
| Тип документа можно выбрать вручную | кнопка типа в панели ввода («Определить автоматически» / один из типов / «Другой документ») и рейка «Тип документа» в ответе — в один клик пересчитывает как другой тип |
| Карточка полей, «не найдено» | блок «Карточка документа»: все поля типа, что не найдено — так и написано; уверенность распознавания у каждого значения |
| Три вида ответов с формулировками из ТЗ | «Заключение» со штампом: «В порядке» / «Не хватает» / «Ответа нет» и текст ответа |
| Источник: пункт Положения или поле документа | чипы «Источник»: клик по «п. 3.4» открывает боковую панель с текстом пункта и соседними пунктами; клик по полю — приближает снимок |
| Бонус: подсветка на снимке | рамки на листе и **вырезка фрагмента фото** прямо в ответе; наведение на строку карточки подсвечивает поле, камера плавно подлетает к нему |
| Бонус: автоопределение типа | рейка типа показывает, как определён тип и с какой уверенностью; для чужих документов — «не похож ни на один из известных» |
| Бонус: новый тип без кода | вкладка «Типы документов»: YAML-редактор с проверкой на лету, номерами строк и живым списком полей |

Сцена пустого стола — лоток для документа и «примеры на столе» (клик по примеру сразу запускает проверку). Пока идёт проверка, **реальные этапы** (файл → чтение текста → тип → карточка → ответ), луч сканера над листом, время и кнопка остановки (`Esc`). Ответ приходит «штампом»; предыдущие ответы сворачиваются в строки, диалог можно продолжать вопросами по тому же документу.

Приёмы интерфейса: масштаб колесом и щипком, перетаскивание, миникарта при увеличении, двойной щелчок — приблизить; `Ctrl+K` — палитра команд (переходы, примеры, поиск по пунктам Положения); `Enter` — отправить, `Shift+Enter` — новая строка; `/` — к полю вопроса; `?` — подсказка по клавишам. Тема: светлая («дневной стол»), тёмная («ночная лампа») или как в системе. История вопросов хранится только в браузере, без снимков. Результат можно скачать в JSON или распечатать (в печать идёт только заключение и карточка).

Дополнительные удобства:
* **Другой документ.** Над снимком — кнопка «Другой документ» и лента документов на столе: можно положить второй файл, проверить его и вернуться к первому, не теряя ответов. Для только что положенного файла появляется кнопка «Проверить документ целиком».
* **Спросить дальше.** Под ответом — вопросы, которые сервис точно умеет разобрать (по найденным полям, правилам Положения, для чужого документа — по его тексту): один щелчок, и вопрос уходит по тому же документу.
* **Копировать ответ** (вердикт, текст и источник) и **сохранить снимок с подсветкой** (PNG с рамками найденных полей) — для переписки со студентом или отчёта.
* **Контраст.** Переключатель в панели снимка повышает контраст бледных и тёмных фото, чтобы глазами сверить результат OCR.
* **Изменить вопрос** (карандаш у реплики), `↑` в пустом поле возвращает прошлый вопрос.
* Мобильная раскладка: стол сверху, диалог под ним; панель ввода компактная.

#### Документ не из вуза («другой документ»)

Классификатор умеет говорить «это не мой тип»: приказ, постановление, счёт, договор не подгоняются под справку. В этом случае сервис честно сообщает, что тип не определён, и отвечает **по тексту самого документа**: по нумерованному пункту («Что приказано в п. 1.2?»), по реквизитам шапки («Какая дата документа?», «Какой номер?»), по значению рядом с названием («ИНН», «Итого»), по смыслу («Сколько мешков с песком нужно?») и «О чём документ?». Ответ даётся только из распознанного текста, с рамкой на снимке; нет подходящего места — «ответа нет». Вопросы о правилах (Положение) работают и для таких документов. Режим можно выбрать и вручную — «Другой документ». Рукописный текст (дату и номер, вписанные от руки в шапку) Tesseract читает плохо: на вопрос «какая дата / какой номер документа?» сервис в этом случае честно отвечает, что реквизит не прочитан, и просит сверить со снимком, а не подставляет случайную строку. Белый лист во весь кадр не обрезается по блоку текста: рамка листа ищется только там, где он заметно отличается от фона.

> Набор [MWS-Vision-Bench](https://huggingface.co/datasets/MTSAIR/MWS-Vision-Bench) — это общий бенчмарк OCR/понимания документов, **не** данные кейса (там нет студенческих справок и Положения). Он нужен только для проверки качества распознавания (`scripts/eval_mws_vision.py`); документ из него не обязан попадать в один из трёх типов — и теперь сервис ведёт себя с ним предсказуемо.

Вкладка **«Положение»** — просмотр, поиск и загрузка своего Положения (`.md`, `.txt`, `.docx`, `.pdf`). Вкладка **«Типы документов»** — просмотр и редактирование YAML-описаний, проверка и сохранение, создание нового типа.

### Командная строка

```bash
python -m dekanat ask data/samples/sample_02.png "Хватит ли этой справки для перевода на 2 курс?" --highlight out.png
python -m dekanat ask scan.pdf "Чего не хватает?" --type academic_leave --json
python -m dekanat ocr photo.jpg                    # только распознавание
python -m dekanat doctor                           # проверка окружения
python -m dekanat validate-config                  # проверка YAML типов документов
```

### Пакетный режим и results.json

Для автопроверки: на вход — список заданий (JSON, JSONL или CSV), на выход — `results.json`.

```bash
python -m dekanat batch --input examples/tasks.json --out results.json --images-dir data/samples
```

Вход распознаёт разные имена колонок: `id`, `image`/`file`/`path`/`file_name`, `question`/`query`, `doc_type`/`type`. Задание без файла — вопрос только по Положению. Ошибка на одном файле не останавливает остальные. Пример результата — `examples/results.example.json`.

Запись результата:

```json
{
  "id": "demo-2", "image": "sample_02.png", "question": "Хватит ли этой справки для перевода на 2 курс?",
  "doc_type": "study_certificate", "doc_type_title": "Справка об обучении",
  "fields": {
    "ФИО студента": "Степанова София Сергеевна", "Название вуза": "Кубанский институт управления и права",
    "Номер и дата выдачи": "номер выдачи: 2172 (не найдено: дата выдачи)", "Подпись и печать (есть/нет)": "нет"
  },
  "answer": "Не хватает даты выдачи и печати вуза. Эти поля обязательны по п. 3.4 Положения.",
  "verdict": "missing", "sources": ["п. 3.4"], "missing": ["даты выдачи", "печати вуза"], "notes": []
}
```

> **Важно про формат.** Точный формат `results.json` описан в README к набору данных организаторов, а его в архиве с ТЗ нет. Формат выше — разумное предположение. Если организаторы требуют другие ключи, меняется одна функция — `result_record()` в [`dekanat/export.py`](dekanat/export.py) (и, при другом формате входных файлов, `read_batch_input()` там же).

### REST API

```bash
curl -F "file=@sample_02.png" -F "question=Хватит ли справки для перевода?" -F "doc_type=auto" http://127.0.0.1:8000/api/analyze
```

Документация OpenAPI — `http://127.0.0.1:8000/api/docs`. Основные методы: `POST /api/analyze` (синхронно, для скриптов), `POST /api/jobs` + `GET|DELETE /api/jobs/{id}` (фоновая задача с прогрессом и отменой — её использует интерфейс), `GET /api/health`, `GET /api/doctypes`, `GET|PUT /api/regulation`, `GET /api/doctypes/{id}/yaml`, `PUT|DELETE /api/doctypes/{id}`, `POST /api/doctypes/validate`. Параметр `doc_type`: `auto`, id типа или `generic` («другой документ»).

## Интерфейс на React

Исходники — в [`frontend/`](frontend/): React 19 + TypeScript (strict) + Vite, тесты — Vitest и Testing Library. Сборка кладётся в `dekanat/web/static/app/` и **закоммичена**, поэтому Python-серверу Node не нужен.

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173, запросы /api проксируются на :8000 (запустите python -m dekanat serve)
npm test           # 54 теста: API-клиент и опрос задач, диалог (useDesk), заключение, карточка полей, выбор типа и документа, «спросить дальше», YAML-помощники
npm run build      # проверка типов + сборка в ../dekanat/web/static/app
```

Устройство: `src/api.ts` — клиент и опрос фоновой задачи с отменой; `src/hooks/useDesk.ts` — диалог (реплики, прогресс, отмена, перезапуск с другим типом); `src/components/desk/` — панель ввода и выбор типа, лента диалога, разбор в реальном времени, заключение со штампом, карточка полей, лоток и просмотрщик снимка (масштаб/щипок/миникарта/луч/рамки); `src/components/` — навигация, палитра команд, панель пункта; `src/views/` — стол, Положение (оглавление со scroll-spy), редактор типов; `src/styles/` — слои CSS, токены и тёмная тема через `light-dark()`. Без сторонних UI-библиотек: анимации — CSS (пружины `linear()`, `@starting-style`) и небольшие хуки. Доступность: семантическая разметка, фокус и клавиатура везде, `aria-live` для статусов, `prefers-reduced-motion` отключает движение; вёрстка подходит для телефона.

## Данные организаторов

Сервис не привязан к конкретному Положению: **замените файл** `data/regulations/polozhenie.md` (или путь в `config/settings.yaml` → `regulation.path`, или загрузите файл во вкладке «Положение»). Нумерация пунктов определяется автоматически: «3.4.», «п. 3.4», «3.4)», разделы «## 3. …» / «Раздел 3», подпункты «а)», «1)», «-». Если нумерации нет — абзацы нумеруются «§1», «§2». Вложенное в репозиторий Положение — **учебное, вымышленное**.

Если типы документов у организаторов отличаются от трёх встроенных — опишите их в YAML (см. ниже), код менять не нужно.

## Как это работает

| Модуль | Что делает |
|---|---|
| `dekanat/ocr/preprocess.py` | загрузка JPG/PNG/PDF (EXIF-поворот), поиск листа на фото и перспектива, оценка наклона по строкам текста (до ±45°), выравнивание тени и освещения, стирание линий таблиц, поиск бликов |
| `dekanat/ocr/runner.py` | проходы Tesseract по нескольким вариантам предобработки с остановкой, когда качество достаточно; оценка качества без эталона; OSD для страниц, повёрнутых на 90/180°; увеличение мелкого текста; матрица «исходное фото → обработанное» для подсветки |
| `dekanat/extract/` | поиск названий полей с допуском на опечатки OCR (стемминг + нечёткое сравнение), значение справа/ниже метки, многострочные значения, регулярные выражения для документов «сплошным текстом», запасные детекторы; разбор дат (в т.ч. «О1.О9.2О23»), ФИО, номеров, оценок, периодов |
| `dekanat/extract/marks.py` | подпись и печать **по изображению**: слова «М.П.» и «(подпись)» есть и на пустом бланке, поэтому ищем сами чернила (цветные кольца и пятна, штрихи вне распознанного текста) |
| `dekanat/classify.py` | автоопределение типа документа |
| `dekanat/kb/` | разбор Положения на пункты; BM25 по основам слов + синонимы; **вывод обязательных полей из текста Положения** |
| `dekanat/qa/engine.py` | намерение вопроса (комплектность / значение поля / правила), три вердикта, источники |
| `dekanat/qa/llm.py` | необязательный «арбитр» на локальной модели (Ollama) |
| `dekanat/web/` | FastAPI + интерфейс без сборки (HTML/JS/CSS) |

### Как выбирается «что обязательно»

Положение читается как данные, а не зашивается в код. Пункт относится к типу документа, если называет его (или стоит в разделе с таким названием). Поле «требуется» пунктом, если пункт его называет и сформулирован обязывающе. Сила формулировки: «обязательны», «не принимается» → «должна содержать», «необходимо» → «указываются». Для поля берётся пункт с самой сильной формулировкой, поэтому недостающие дата и печать ссылаются на п. 3.4 («обязательными реквизитами… не принимается»), а не на перечень в п. 3.2; если всё на месте — называется пункт-перечень (п. 3.2). Если Положение вообще не называет требований к типу документа, используется `required_fallback` из конфига, и ответ прямо об этом сообщает.

### Как формируется ответ

* **Проверка комплектности** («хватит ли…», «подойдёт ли…», «чего не хватает…», пустой вопрос): недостающие поля сгруппированы по пунктам. Если вопрос про цель, для которой Положение называет *другой* документ, ответ об этом скажет.
* **Значение поля** («какая форма обучения указана?», «кто руководитель практики?»): значение из карточки + поле-источник. Поле не найдено, но обязательно → вердикт «не хватает» с пунктом.
* **Правила** («за какой срок рассматривается заявление?»): ближайший пункт Положения, дословно, с номером.
* **Нет данных**: если слова вопроса не покрываются ни одним пунктом (а «редкие» слова вроде «стоит», «стипендия», «общежитие» не найдены вовсе), ответ — «нет информации». Слова-уточнения («максимальный срок») отказ не вызывают.
* Опционально (`llm.backend: ollama`): на пограничных вопросах локальная модель решает *только* «есть ли ответ в этих пунктах и в каком». Текст ответа всё равно берётся из Положения. Модель не обязательна: без неё сервис просто осторожнее (чаще «ответа нет»).

## Настройка

`config/settings.yaml` — все параметры с комментариями; любой можно переопределить переменной окружения `DEKANAT_<РАЗДЕЛ>_<КЛЮЧ>` (например, `DEKANAT_OCR_TESSERACT_CMD`, `DEKANAT_LLM_BACKEND=ollama`, `DEKANAT_SERVER_PORT=9000`).

Для лучшей точности OCR можно подложить данные `tessdata_best` (rus, eng, osd) в отдельную папку и указать её в `ocr.tessdata_dir` — это самый простой способ улучшить чтение сложных снимков.

### Описание типа документа (YAML)

Минимальный пример (полные — в `config/doc_types/`):

```yaml
id: scholarship_certificate           # латиница, строчные, цифры, «_»
title: Справка о стипендии
short_title: Справка                  # «Справка содержит все данные…»
genitive: справки о стипендии
aliases: [справка о стипендии]        # как документ называют в Положении (для привязки пунктов)
classify:                             # автоопределение типа
  keywords:
    - {phrase: справка о стипендии, weight: 7}
  negative:
    - {phrase: академический отпуск, weight: 5}
fields:
  - id: student_name
    title: ФИО студента               # название в карточке и в results.json
    kind: person
    labels: [ФИО студента, ФИО, Студент]            # как поле подписано в документе
    mention: [ФИО студента]                          # как поле называется в Положении (по умолчанию — title и многословные labels)
    patterns: ['(?i:студент(?:ка)?)\s+(?P<value>{FIO})']   # для текста «сплошным абзацем»; макросы {DATE} {FIO} {NUM}
    missing_phrase: ФИО студента      # «Не хватает …» (родительный падеж)
  - id: amount
    title: Размер стипендии
    kind: number
    labels: [Размер стипендии, Сумма]
    missing_phrase: размера стипендии
```

Виды полей (`kind`): `person`, `org`, `text`, `date`, `number`, `choice` (нужен `choices`), `period`, `grade`, `group`, `course`, `composite` (части в `parts`, например «Номер и дата выдачи»), `marks` (подпись/печать, части с `mark: signature | stamp`). Дополнительно: `multiline: true`, `fallback: header_org | unclaimed_date_last`, `format` для составных, `export_title`, `checks` (проверка порядка дат), `required_fallback`.

Проверка конфига: `python -m dekanat validate-config`. В интерфейсе: «Типы документов» → «Проверить» / «Сохранить» (применяется сразу, без перезапуска). Тест `tests/test_new_doctype.py` показывает полный путь: новый тип + пункты Положения + документ → корректный ответ без правок кода.

## Качество и оценка

Данных организаторов в архиве нет, поэтому качество проверялось на **синтетических документах**, которые генерирует сам проект (`python -m dekanat synth`): три типа документов × три вёрстки (форма, таблица, сплошной текст), шрифты, рукописная подпись и круглая/прямоугольная печать, «дефекты» (нет даты, номера, подписи, печати…) и три уровня порчи: 0 — чистый скан, 1 — лёгкое фото, 2 — тяжёлое фото (наклон до 30°, тень, блик, перспектива, ≈900 px по ширине, JPEG q45–70).

```bash
python -m dekanat synth --out data/synthetic --n 6 --levels 0,1,2 --seed 101   # документы + эталон + вопросы
python -m dekanat eval --data data/synthetic --verbose                          # полный путь, как у автопроверки
python -m dekanat eval --data data/synthetic --oracle                           # только логика ответов (OCR не нужен)
```

Результат на **свежем наборе** (seed 101: 54 документа, 146 вопросов), который не использовался при настройке; ноутбук без GPU, ≈1–3 с на страницу:

| Метрика | Чистые сканы | Лёгкие фото | Тяжёлые фото | Всего |
|---|---|---|---|---|
| Тип документа (автоопределение) | 18/18 | 18/18 | 18/18 | **100 %** |
| Поля карточки (допуск ≤10 % на опечатки OCR) | 98,7 % | 98,1 % | 85,3 % | **94,0 %** (строго — 92,1 %) |
| Подпись и печать (есть/нет) | — | — | — | 95,6 % (86/90) |
| Вердикт ответа (в порядке / не хватает / нет ответа) | 97,8 % | 100 % | 90,6 % | **95,9 %** (140/146) |
| Ссылка на верный пункт Положения | 96,2 % | 100 % | 96,4 % | **97,4 %** (76/78) |

По видам вопросов: правила — 24/24, «ответа нет» — 16/16, значение поля — 49/52, комплектность — 51/54. Точное совпадение *списка* недостающих полей — 72 % (21/29): на тяжёлых фото OCR иногда «теряет» ещё и соседние поля.

Отдельно проверялась логика ответов на **разговорных формулировках** (`tests/test_qa_heldout.py`). На первом честном прогоне свежего набора из 26 разнообразных, местами намеренно каверзных вопросов («Справка полная?», «Мне могут отказать из-за справки?», «До какого числа действует справка?») результат был **50 %** (13/26). Разобрав ошибки, я исправил общие лексические пробелы (синонимы, обороты), после чего эти вопросы стали регрессионными тестами — их 98 % уже не «независимая» оценка. Реалистичный ориентир для действительно незнакомых формулировок — ближе к первым 50–75 %: подход лексический, а не семантический.

**Оговорки.** (1) Синтетические документы нарисованы тем же проектом, на котором настраивались эвристики: на реальных данных организаторов цифры будут ниже, особенно для подписи/печати и нестандартных вёрсток. (2) Вопросы в наборе составлены из тех же пулов формулировок, что и в разработке — поэтому метрики ответов выше, чем на разговорной речи (см. абзац выше). (3) Самое слабое звено — тяжёлые фото низкого разрешения: текст там нередко физически нечитаем. (4) Данных организаторов (документов, Положения, вопросов) в архиве с ТЗ нет — на них проект не запускался.

### MWS-Vision-Bench

[MWS-Vision-Bench](https://huggingface.co/datasets/MTSAIR/MWS-Vision-Bench) — общий бенчмарк русскоязычных бизнес-документов для мультимодальных моделей (сканы, таблицы, рукописные документы; задания: парсинг документа, OCR страницы, извлечение ключевой информации, VQA, привязка текста). Справок и Положения вуза в нём нет, поэтому он **не заменяет** данные организаторов, но подходит для проверки звена OCR на документах разного качества. Скрипт `scripts/eval_mws_vision.py` считает CER «полного пайплайна» против «голого» Tesseract на заданиях «full-page OCR»; датасет (≈820 МБ) в репозиторий не входит и сам не скачивается — только по явному `--download N`:

```bash
python scripts/eval_mws_vision.py --root data/mws --download 15 --limit 15      # скачает metadata.jsonl и 15 изображений
python scripts/eval_mws_vision.py --root D:/datasets/MWS-Vision-Bench --limit 30 # локальная копия
```

## Ограничения (честно)

* **Формат данных и `results.json` организаторов неизвестен** — см. выше, что менять.
* **OCR — только Tesseract** (в установленной здесь версии файл `rus.traineddata` занимает около 4 МБ — это компактная модель; `tessdata_best` обычно точнее). EasyOCR/PaddleOCR не подключены: интерфейс движка (`OcrRunner` ↔ `TesseractEngine`) простой, но других движков в проекте нет. Типичные ошибки: путаница «Э»/«3», «Ф»/«0» в кодах групп (код при этом считается найденным), потеря символов на нечитаемых снимках.
* **Подпись и печать — эвристика по изображению.** Подпись поверх печати того же цвета может не найтись; крупный нераспознанный печатный текст у линии подписи иногда похож на подпись. У каждой находки есть уверенность и рамка.
* Срок действия справки («действительна 30 дней») **намеренно не проверяется** — для этого нужна дата «сегодня», а результат зависел бы от дня проверки.
* Положение читается как «пункты текста»: сложные таблицы, примечания и ссылки между пунктами не разбираются. В `.docx` автонумерация Word восстанавливается приблизительно.
* Нет Telegram-бота (в ТЗ интерфейс «любой»: сделана веб-страница).
* Нет авторизации: сервис рассчитан на локальный запуск (`127.0.0.1`). Не открывайте его в интернет с `allow_edit: true`.
* Локальная модель (Ollama) — необязательное дополнение: на CPU один вызов занимает 10–30 с.
